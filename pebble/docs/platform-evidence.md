# Pebble Time 2 platform evidence (2026-10-18)

Read-only discovery plus this evidence document; no project code/tests changed. Official SDK/web docs were fetched live. The official Pebble mobile-app public mirror is pinned below at commit `ec2156cc38a850e5458addba2a2fb8efa34396df` (2026-10-08). **Do not confuse source-mirror head with an App Store build number**: its [README](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/README.md) says the public mirror is synced manually and may lag. A current released-app runtime feature probe is required before depending on the config bridge.

## Hardware and target

- [Official Pebble hardware table](https://developer.rebble.io/guides/tools-and-resources/hardware-information/#platform-support) lists **Pebble Time 2 = Emery**, 1.5-inch rectangular 200×228 64-colour display, touchscreen, microphone (two, second for ENC), and speaker. [Official store](https://repebble.com/watch) likewise advertises the 1.5-inch 64-colour e-paper touchscreen, steel frame, HR monitor and microphone; it lists the Time 2 speaker as present. Product/in-stock status is store-dependent; do not describe any hardware as planned/unshipped based on the 2025 preorder page.
- `pebble-tool` stable **5.0.40** is at [Core Devices GitHub release](https://github.com/coredevices/pebble-tool/releases/tag/v5.0.40), published 2026-08-25; PyPI reports Python `>=3.10`. Official [SDK installation page](https://developer.rebble.io/sdk/) requires Python 3.10+ and Node on macOS and documents `uv tool install pebble-tool --python 3.13`; it notes v5.0.18 did not support Python 3.14. Current official SDK index [metadata](https://sdk.repebble.com/v1/files/sdk-core?channel=) currently lists **4.33.1** as latest stable, package metadata at [`/v1/files/sdk-core/4.33.1?channel=`](https://sdk.repebble.com/v1/files/sdk-core/4.33.1?channel=), archive [`sdk-core.tar.gz`](https://sdk.repebble.com/releases/4.33.1/sdk-core.tar.gz), and [release notes](https://developer.rebble.io/sdk/changelogs/4.33.1/). This exact SDK archive was inspected; `pebble/emery/include/pebble_process_info.h` identifies SDK API version **5.106** (`0x5.6a`). Its generated `pebble/emery/include/pebble.h` exports touch, Dictation, and Speaker APIs. Build target is `emery`.
- Official platform config `tools/pebble_sdk_platform.py` in [PebbleOS source](https://github.com/coredevices/PebbleOS/blob/main/tools/pebble_sdk_platform.py) sets Emery `MAX_APP_BINARY_SIZE=128 KiB`, `MAX_APP_MEMORY_SIZE=128 KiB`, resource limit 1 MiB (App Store 256 KiB), and `PBL_TOUCH`, `PBL_SPEAKER`, `PBL_MICROPHONE`, `PBL_COLOR`, `PBL_RGB_BACKLIGHT`, 200×228. Official Hardware Information calls the 128 KiB ceiling “Max App Size (code + heap)”. This is **not 128 KiB free heap**: firmware `fw/process_management/app_manager.c` allocates a 4 KiB native app stack on Emery, and app state/stack guard also consume the configured 135,168-byte 4.x app RAM segment (`Kconfig` `APP_RAM_EMERY_SEGMENT_SIZE`); only remaining app segment is heap. Moddable JS apps get an 8 KiB stack. Exact user-available heap is build/app dependent.
- AppMessage has guaranteed `APP_MESSAGE_INBOX_SIZE_MINIMUM=124` bytes and `APP_MESSAGE_OUTBOX_SIZE_MINIMUM=636` bytes (`fw/applib/app_message/app_message.h`). For an API-SDK-5.63+ app **and** phone advertising `CommSessionAppMessage8kSupport`, current OS `app_message.c` allows one dictionary with 8 KiB data (`APP_MSG_8K_DICT_SIZE` includes dictionary/tuple overhead). SDK 4.33.1’s API version is 5.106, and current iOS phone capabilities include `Supports8kAppMessage`; runtime maximum remains `app_message_*_size_maximum()` rather than an unconditional fixed AppMessage payload size. AppMessage consumes app heap; do not send audio or large history on it.

## Touch and beeper (speaker)

- Official [Touch guide](https://developer.rebble.io/guides/events-and-services/touch/) describes `touch_service_subscribe`, raw touchdown/position/liftoff events, recognizers, and `app_touch_navigation_enable(true)`; it explicitly says raw TouchService is **watchapp-only**, not watchfaces. User may disable touch (`touch_service_is_enabled()`; graceful button fallback required). Firmware 4.32 introduced system touch navigation. SDK 4.33.1 notes it installs on firmware 4.33/4.33.1 and its recognizer crash fix only ships in firmware 4.33.2; do not assume all currently installed watches have that bug fix.
- Official [Speaker guide](https://developer.rebble.io/guides/events-and-services/speaker/) confirms app-facing one-shot synthesized beeps and notes (`speaker_play_tone(440, 250, 80, SpeakerWaveformSine)` or `speaker_play_notes(...)`), not merely system alert sound. Emery defines `PBL_SPEAKER`; the SDK generated API header exports `speaker_play_tone`, `speaker_play_notes`, `speaker_is_muted` (the API metadata marks Speaker `appOnly`). APIs return false when unsupported/busy. `speaker_is_muted()` tells whether the user globally muted sound or Quiet Time muted it; official SDK header says apps **cannot override mute**. Respect it and provide visual/vibration fallback. Speaker playback is power hungry; keep notification beeps short.

## Dictation is not arbitrary app audio/cloud speech

- Official [Dictation C API docs](https://developer.rebble.io/docs/c/Foundation/Dictation/) export `dictation_session_create/start/stop`, `dictation_session_enable_confirmation` (confirmation defaults on), and status enums. The official [guide](https://developer.rebble.io/guides/events-and-services/dictation/) explains the dictation UI: mic audio travels through the phone app to a third-party recognizer; user reviews text, Back rejects/retries, Select accepts; absent phone/app/network or disabled recognition fails. This is a platform dictation feature/service, **not a documented raw-microphone recording API for arbitrary cloud uploads**, and cannot justify inventing an audio API or paid provider.
- Official current-companion public source [`VoiceSessionManager.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/libpebble3/src/commonMain/kotlin/io/rebble/libpebblecommon/connection/endpointmanager/audio/VoiceSessionManager.kt) implements the provider gate; [`STTRouter.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/commonMain/kotlin/coredevices/pebble/services/STTRouter.kt) routes modes; [`RebbleAsrTranscription.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/commonMain/kotlin/coredevices/pebble/services/RebbleAsrTranscription.kt) availability requires a logged-in Rebble account plus nonempty boot-config `voice.languages`; [`RebbleAsrService.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/commonMain/kotlin/coredevices/pebble/services/RebbleAsrService.kt) uploads over HTTPS to configured `/NmspServlet/` and explicitly maps 402 to “subscription required” and 401 to auth failure. Other modes require build-configured Wispr/Kirinki URLs or a local model; `VoiceSessionManager` answers `FailDisabled` if no provider can serve. Do **not** assume anonymous, enabled, or free RePebble dictation. For mandatory voice add a real provider-availability gate and fail closed. Review/cancel/explicit Send belongs to app-level UI: do not send a draft until the user confirms; dictation acceptance is not message-send consent.

## Pairing and phone bridge

- Official developer [Communication guide](https://developer.rebble.io/guides/communication/) says the watch communicates via AppMessage over its paired phone's Bluetooth connection; the receiving endpoint is either PebbleKit JS in the official companion **or** native PebbleKit iOS/Android, not both. JS is the practical supported bridge for the paired phone. The official current mobile source README says watch has no Internet and the phone app is persistent BLE gateway/proxy; PKJS is phone-side.
- Legacy native [`pebble/pebble-ios-sdk`](https://github.com/pebble/pebble-ios-sdk) exists (`pod 'PebbleKit'`) but registers its own `PBPebbleCentral`/watch connection and App Store whitelisting. Current official Pebble app’s `libpebble3/src/iosMain/.../CompanionAppLifecycleManager.ios.kt` expressly returns `null`: “PebbleKit iOS does not work through the phone - nothing to do here.” Thus not a legitimate bridge into the existing pairing. This is an implementation-specific current-app fact, not a claim that third-party PebbleKit is universally impossible.

## Practical auth provisioning decision

- **Verdict:** no per-watchapp native secure-secret setting/API was found in inspected public source. Legacy config-page submission sends `encodeURIComponent(JSON.stringify(options))` in a `pebblejs://close#...` URL and returns it as `e.response` ([official guide](https://developer.rebble.io/guides/user-interfaces/app-configuration-static/)); never put bearer secrets in this close URL. Official PebbleKit JS docs say `localStorage` persists across uninstall/reinstall/upgrades; current iOS implementation stores it in `NSUserDefaultsSettings.Factory().create("PKJS-$id")` (Android uses SharedPreferences), **not a secret vault**. `PrivatePKJSInterface.onConsoleLog` also relays original console text into a log channel even when its logger redaction branch runs; never `console.log` credentials.
- **Practical source-supported option (ephemeral RAM only):** current public source [`ConfigPageBridge.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/commonMain/kotlin/coredevices/pebble/config/ConfigPageBridge.kt), [`ConfigPageSession.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/commonMain/kotlin/coredevices/pebble/config/ConfigPageSession.kt), [`WatchappSettingsScreen.ios.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/iosMain/kotlin/coredevices/pebble/ui/WatchappSettingsScreen.ios.kt), [`PKJSApp.kt`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/libpebble3/src/commonMain/kotlin/io/rebble/libpebblecommon/js/PKJSApp.kt), and [`startup.js`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/libpebble3/src/androidMain/assets/startup.js) implement phone-side config-page IPC: page calls `Pebble.sendMessage(target,data)`; target is literal `"pkjs"`; PKJS receives `configmessage` whose only trust-relevant app data field is `e.data` (an app-defined object) and must call `e.respond(reply)`. `Pebble.targets()` returns `[{id,name}]`; `sendMessage` returns a Promise with the response. Working example [`weather-face/src/pkjs/index.js`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/test-apps/weather-face/src/pkjs/index.js#L121-L168) registers `showConfiguration` and `configmessage`, and its page feature-detects on use, sends `"pkjs"`, and awaits the reply. Its [package.json](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/test-apps/weather-face/package.json) declares `capabilities:["configurable"]`; in a production PBW use app metadata `pebble.configPage` to name a bundled HTML page. The official companion resolves a bundled config file from the PBW into a `data:text/html` URL; **hosting a config page is not mandatory**. This is a custom current-companion API, **not** the legacy PebbleKit JS SDK contract. Minimal shape:

  ```js
  // App-owned phone config page; password field is not submitted in the close URL.
  async function provision(token) {
    if (typeof Pebble.sendMessage !== "function" || typeof Pebble.targets !== "function")
      throw new Error("This Pebble app does not support secure provisioning");
    const targets = await Pebble.targets();
    if (!targets.some(target => target.id === "pkjs")) throw new Error("PKJS unavailable");
    return Pebble.sendMessage("pkjs", {type: "credential", token});
  }
  
  // Phone-side PKJS module scope: RAM only; no localStorage, AppMessage or logging.
  let credential;
  Pebble.addEventListener("configmessage", event => {
    const message = event.data;
    if (message?.type !== "credential" || typeof message.token !== "string" ||
        message.token.length === 0 || message.token.length > 4096)
      return event.respond({ok: false});
    credential = message.token;
    event.respond({ok: true});
  });
  // Later use only fixed HTTPS endpoint, Authorization header/body, app-domain permission.
  // Do not print token, request headers/body, or token-bearing exceptions.
  ```

  `XMLHTTPRequestManager.kt` supports POST/body and custom headers; `PluginNetworkPolicy`/`NetworkGate` enforce `Internet/<domain>` permission when plugin permissions are enabled. No backend route is specified here. `PKJSApp.kt` says the PKJS session already runs whenever its config page is open: opening/closing that page alone need not kill the RAM token. `CompanionAppLifecycleManager.kt` stops PKJS when app-run state stops/changes; app exits, phone connection/runtime recreation, or companion process death clears RAM. Therefore prompt/re-auth after stop/restart. Durable localStorage is a convenience tradeoff, **not** recommended for a bearer.
- **Feature/origin gate and release limitation:** `ConfigPageSessions.enabled` reads `WatchConfig.enablePlugins` (default false), and `Locker.appConfigPageUrl()` returns null when plugins are disabled. The IPC exists only in current mobile source and must be feature-probed (`Pebble.targets()` includes `pkjs`; `Pebble.sendMessage` exists); absent API/session → fail closed, never fallback with a secret in a legacy URL. iOS `WKScriptMessageHandler` forwards only JSON body to `ConfigPageBridge.onCall`; it does **not** check `WKScriptMessage.frameInfo.securityOrigin`, and no origin/provenance field is present in the event. No app-issued CSP/origin allowlist was found on this bridge; a browser CSP supplied by an app-controlled page is possible, but source evidence does not show the host enforcing one. Prefer the bundled PBW `configPage` data URL with app-owned inline code (no remote scripts), or fixed HTTPS origin under the app owner’s control without untrusted content/redirects; the bridge is not origin-authenticated. PKJS `Pebble.openURL` is permission-checked by `JsRunner.mayOpen`, but source can choose the page URL. Public mobile-app source commit was **2026-10-08**; its README warns the source mirror sync is manual and may lag. No exact signed App Store build was matched to this API. Runtime feature-probe and fail closed.

## Bearer redirect handling: source proof, runtime gate

- PKJS XHR attaches Basic auth (if present) and every JS-supplied request header to Ktor `client.request` ([exact mobile-source line range](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/libpebble3/src/commonMain/kotlin/io/rebble/libpebblecommon/js/XMLHTTPRequestManager.kt#L188-L207)). On iOS `JavascriptCoreJsRunner` passes the injected `HttpClient` to that manager ([lines 86–99](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/libpebble3/src/iosMain/kotlin/io/rebble/libpebblecommon/js/JavascriptCoreJsRunner.kt#L86-L99)); `PKJSModule.ios.kt` obtains it from DI ([lines 9–31](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/libpebble3/src/iosMain/kotlin/io/rebble/libpebblecommon/di/PKJSModule.ios.kt#L9-L31)). In that graph the injected client is built in `pebble/watchModule.kt` ([lines 239–245](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/pebble/src/commonMain/kotlin/coredevices/pebble/watchModule.kt#L239-L245)) with ContentNegotiation and **no** `followRedirects`, `HttpRedirect`, or auth override. The Ktor version is **3.5.1** (`gradle/libs.versions.toml:8` in the pinned mobile source).
- iOS engine is `Darwin.create` ([`iosDefaultModule.kt:51–57`](https://github.com/coredevices/mobileapp/blob/ec2156cc38a850e5458addba2a2fb8efa34396df/composeApp/src/iosMain/kotlin/coredevices/coreapp/di/iosDefaultModule.kt#L51-L57)); PKJS uses the Darwin engine dependency (`libpebble3/build.gradle.kts:143–145`). Ktor 3.5.1’s [default config](https://github.com/ktorio/ktor/blob/3.5.1/ktor-client/ktor-client-core/common/src/io/ktor/client/HttpClientConfig.kt#L87-L96) has `followRedirects=true`. The [core client](https://github.com/ktorio/ktor/blob/3.5.1/ktor-client/ktor-client-core/common/src/io/ktor/client/HttpClient.kt#L1377-L1392) installs `HttpRedirect` when enabled. [Ktor’s Darwin NSURLSession delegate](https://github.com/ktorio/ktor/blob/3.5.1/ktor-client/ktor-client-darwin/darwin/src/io/ktor/client/engine/darwin/KtorNSURLSessionDelegate.kt#L134-L146) explicitly declines Foundation’s embedded redirect (`completionHandler(null)`), so the Ktor plugin—not NSURLSession—handles redirection. The [Ktor redirect handler](https://github.com/ktorio/ktor/blob/3.5.1/ktor-client/ktor-client-core/common/src/io/ktor/client/plugins/HttpRedirect.kt#L17-L46) allows only GET/HEAD by default, blocks HTTPS downgrade, and [removes the standard `Authorization` header before a cross-authority follow](https://github.com/ktorio/ktor/blob/3.5.1/ktor-client/ktor-client-core/common/src/io/ktor/client/plugins/HttpRedirect.kt#L85-L105).
- **Source-scoped verdict:** in this graph, standard `Authorization: Bearer` is not forwarded to a different-authority redirect for a GET/HEAD; a POST redirect is not followed by default; same-authority redirects retain Authorization. Only the standard Authorization header is stripped—do not put bearer material in custom headers. XHR checks network permission for the initial URL before request, not each redirect hop (`XMLHTTPRequestManager.kt:188–207`); therefore pin/enforce fixed HTTPS origin/path in app code and backend regardless.
- **Release gate remains:** this proves behavior of the public **source mirror at commit `ec2156cc…`**, not the currently installed signed iOS/Android app build. No runtime build fingerprint was obtained. The auth feature remains gated until the running companion is identified as containing this code/API; do not generalize this source result into a universal PebbleKit guarantee.
